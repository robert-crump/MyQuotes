2026-09-19 — Issue #23: Backup Destination seam — one backup run for local and Drive

Collapsed the two copy-pasted backup subsystems into one module. New: `BackupDestination` (interface) with `SafDestination` / `drive.DriveDestination` adapters; `BackupRun` (no Android state: encode pretty, hash the written bytes, skip if unchanged, write timestamped file, prune via BackupRetention, return SKIPPED_UNCHANGED / WRITTEN(hash) / FAILED(cause)); `BackupTarget` (per-destination constants; pref file names, channel ids and notification ids 1002/1003 unchanged); `BackupState`, `BackupNotifications`, `BackupScheduler`, and a single `BackupWorker` that picks the destination from input data. `LocalBackup` and `DriveBackup` shrank to thin facades; `LocalBackupWorker`/`DriveBackupWorker` deleted. `DriveBackup.connect(email)` / `disconnect()` fold the DriveAuth flag and the schedule together, so `SettingsActivity` makes one call per transition (four hand-paired sites gone; `DriveAuth.markConnected/disconnect` are now package-private).

Defects closed: local and Drive now write identical pretty-printed bytes and the stored hash is over those bytes (first run after upgrade writes one extra backup because the old stored hash was of the compact string). Backups moved from PeriodicWorkRequest+UPDATE to the self-rescheduling one-shot chain via a new shared `scheduling.WorkChain`, which `QuoteNotifications` now uses too; old periodic jobs are cancelled on startup and the chains use new work names (`backup_local`, `backup_drive`), Drive keeps NetworkType.CONNECTED.

Found while doing this: the #21 fix re-armed from inside `doWork()` with `ExistingWorkPolicy.KEEP`, but the running request still counts as unfinished work under that name, so KEEP is a no-op there and the chain only healed on the next app open. `WorkChain.rearmFromWorker` uses `APPEND_OR_REPLACE` (worker must return success or the appended successor is cancelled), and `DailyQuoteWorker` uses it too. Reasoned from WorkManager's documented semantics, NOT verified on device. Behaviour change: a failed backup run now posts the notification, re-arms, and returns success instead of Result.failure().

Tests: new `BackupRunTest` (skip on unchanged hash, filename parses back to clock timestamp, recorded hash equals hash of received bytes, prune converges on 9 over 15 simulated days, write failure -> FAILED with no hash). Docs: CONTEXT.md (Backup Destination, Backup run, Auto-backup replace the two subsystem entries), ADR-003. Build and all unit tests pass. On-device verification deferred to the user. Issue #23 closed.

2026-09-13 — Issue #21: Daily quote notification silent for weeks, then fired instantly on app open

Diagnosed by elimination rather than logs (no device access): the two usual stock-Android causes for "background work goes silent until the app is reopened" were both ruled out via the user — battery setting was already "Unrestricted" the whole three weeks (rules out Doze/App Standby Bucket throttling), and the app was not force-stopped (rules out the OS cancelling all scheduled work until next manual launch). Device is a Pixel, so no OEM-specific battery manager (e.g. Samsung's separate Sleeping Apps list) is in play either.

That leaves WorkManager's own `PeriodicWorkRequest`: its internal re-arm after each 24h cycle is documented to occasionally fail to persist, and — because `QuoteNotifications.scheduleDailyNotification` used `ExistingPeriodicWorkPolicy.UPDATE`, which explicitly preserves the original enqueue-time bookkeeping — reopening the app wouldn't have self-healed a corrupted schedule even though it happened to "fix" it this time (a fresh cold start's `enqueueUniquePeriodicWork` call still runs unconditionally on every launch via `MyApplication.onCreate` -> `QuoteNotifications.initialize`).

Fixed by replacing the periodic request with a self-rescheduling one-shot chain: `scheduleDailyNotification` now enqueues a single `OneTimeWorkRequest` targeting the next ~4 PM, and `DailyQuoteWorker.doWork()` calls it again itself right after showing each notification to arm tomorrow's occurrence, rather than relying on WorkManager to autonomously re-trigger a periodic contract days later unattended. Every call site (app open, boot, the worker) switched from `ExistingPeriodicWorkPolicy.UPDATE` to `ExistingWorkPolicy.KEEP`, so an already-pending schedule is left alone but a missing one (chain broken again, for whatever reason) gets self-healed the next time any entry point runs. See ADR-002 amendment. Side effect: delivery narrows from the old 8 AM-4 PM flex window to a single ~4 PM target, since one-shot requests carry no flex interval.

Build and all unit tests passed. On-device verification of the new schedule (and whether it survives another multi-week idle stretch) deferred to the user. Issue #21 closed.

2026-09-01 — Issue #20: Status bar shows white instead of themed pink (targetSdk 35 edge-to-edge)

Surfaced during on-device verification of #19, but not caused by it — root cause traced back to the `5f88eb5` MD3 migration commit. `app/build.gradle` sets targetSdk 35 (Android 15), and starting on API 35 the platform enforces edge-to-edge and ignores android:statusBarColor/navigationBarColor entirely. themes.xml still set statusBarColor to pink_primary_dark, and every activity layout had android:fitsSystemWindows="true" (added in 5f88eb5), which only pads content down below the status bar rather than painting anything behind it — so with the color attribute ignored, the status bar area went transparent and showed the plain white android:colorBackground behind it instead of pink.

Implemented:
- EdgeToEdgeUtils.java (new) — static apply(Activity, View toolbar) helper: calls WindowCompat.setDecorFitsSystemWindows(window, false), then attaches OnApplyWindowInsetsListener to the toolbar (grows its top padding by the status bar inset so its colorPrimary background paints behind the transparent status bar while title/icons stay clear of it) and to the activity's content root, found via ((ViewGroup) findViewById(android.R.id.content)).getChildAt(0) (pads left/right/bottom by the system bar insets so nothing sits under the nav bar or a side cutout; top padding is left alone since the toolbar already accounts for it).
- Removed android:fitsSystemWindows="true" from all 7 activity root layouts (activity_main, activity_add_edit_quote, activity_categories, activity_favorites, activity_settings, activity_statistics, activity_search) — superseded by the insets listeners.
- Called EdgeToEdgeUtils.apply(this, toolbar) right after setContentView/toolbar lookup in all 7 activities (MainActivity, SettingsActivity, CategoriesActivity, FavoritesActivity, AddEditActivity, StatisticsActivity, SearchActivity).

On-device follow-up #1 (same session, folded into the #20 commit before it was pushed): the fix above caused a second regression — every Toolbar had a fixed android:layout_height="?attr/actionBarSize" (~56dp), so growing its top padding by the status bar inset ate into that fixed height instead of adding to it, squeezing the title/overflow-menu into whatever was left (overflow icon became invisible, content looked shoved up). Fixed by changing all 7 Toolbars from android:layout_height="?attr/actionBarSize" to android:layout_height="wrap_content" + android:minHeight="?attr/actionBarSize", so the inset padding grows the toolbar's total height instead of compressing its content area (the standard pattern for an edge-to-edge app bar).

On-device follow-up #2 (separate commit — the #20 commit had been pushed to origin/main by then, so this landed as a new commit instead of another amend): the two-tone status bar look was lost — padding the toolbar's own top meant its single colorPrimary background painted straight through both the toolbar and the status bar strip, whereas the pre-edge-to-edge app used a visibly darker "variant" shade (pink_primary_dark / purple_primary_variant) behind the status bar specifically. Reverted the toolbar padding approach; instead added a dedicated status_bar_scrim View (height 0dp, grown to exactly the status bar inset at runtime) directly above the Toolbar in all 7 layouts, colored via a new ?attr/statusBarScrimColor theme attribute (attrs.xml; pink_primary_dark in themes.xml, purple_primary_variant in themes_night.xml — the same values the now-ignored android:statusBarColor used to carry). EdgeToEdgeUtils.apply now takes the scrim view instead of the toolbar, and Toolbars went back to their original fixed actionBarSize height since they're no longer padded.

Build and all unit tests passed after each follow-up. On-device verification deferred to the user per their request. Issue #20 closed.
